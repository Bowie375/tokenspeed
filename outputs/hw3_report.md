## 2. 实现与缓存生命周期

### 2.1 实现边界

本实验基于 TokenSpeed 已有的缓存分组、C++ 调度器、Host 存储、快照和完成事件框架，采用现有 Ascend DMA 搬运能力。工作重点是验证两级缓存的完整运行流程、补充容量与淘汰统计，并建立功能正确性及性能对照实验；分配器、淘汰策略和搬运内核沿用框架实现。

| 部分 | 采用的实现及本轮工作 |
| --- | --- |
| 分配与前缀匹配 | 复用统一缓存协调机制，管理 Device/Host 块及请求引用 |
| Host 存储与传输 | 复用 Host 缓存存储与传输机制，通过页锁定主机内存和 NPU 执行流完成 D2H/H2D |
| 活跃请求恢复 | 复用快照保存、恢复及请求槽位状态导出机制，覆盖缓存字段之外的请求状态 |
| TP 完成协调 | 复用跨 rank 完成事件协调机制，对齐完成票据后推进调度器 |
| 新增统计 | 暴露 Host 空闲父块、已发布子块接口；新增累计 Host 容量淘汰计数，显式清空不计为容量淘汰 |
| 新增验证与测量 | 建立端到端数值检查、容量统计和性能对照，并补充真实调度器及 Ascend 搬运回归测试 |

### 2.2 块、引用与回收

Device 缓存采用预分配池，调度器按父块统一核算容量。各缓存组按照自身布局组织子块和字段，分别承载 KV 历史页、GDN 状态及卷积历史。

缓存通过前缀哈希、缓存组、页偏移及已计算上下文边界标识。前缀匹配实现历史缓存复用，GDN 状态的匹配以已保存的检查点为依据。系统通过引用计数和固定标记（pin）管理块的生命周期；请求持有状态、在途传输源块和挂起请求的 Host 数据在相关引用释放后进入可回收状态。

缓存的主要生命周期如下：

1. 调度器为请求分配 Device 块，模型更新对应 rank 的本地 KV、递归状态和卷积状态。
2. 到达可发布边界后，将不可变检查点写入 Host；请求可继续推进后续计算。
3. 普通写回保留 Device 源块引用，直到 D2H 完成事件得到确认。之后，不再被请求使用的 Device 缓存可以保留供复用，也可以在容量压力下淘汰并重新分配。
4. 后续请求优先匹配 Device 缓存，Host 命中时分配目标 Device 块并提交 H2D，各层计算等待对应字段的完成事件。
5. Host 预算不足时，按照框架的访问顺序和容量约束淘汰未被 pin 的缓存项；未命中请求通过普通 Prefill 重建所需状态。

Host 写回与 Device 回收分别由传输完成状态和块引用状态控制。写回后，Device 副本可继续保留供前缀复用；容量压力触发符合条件的块回收。Host 侧则在预算约束下淘汰缓存项。

### 2.3 活跃请求抢占与 TP 协调

活跃请求抢占在其已提交计算完成后进行。调度器保存当前计算边界的状态，将可发布部分写入 Host L2，私有尾部及请求槽位状态写入独立、有界的快照空间。保存操作先于同一调度计划中的清零和块复用操作，通过执行流屏障保证复制与覆盖的顺序。

恢复操作将两个 Host 来源的数据装入新分配的 Device 块，并导入请求槽位状态，全部完成后提交恢复确认。普通 L2 加载通过各层完成事件协调传输与计算。

TP=2 中，每个 rank 搬运本地 head/channel 分片，镜像调度器在各 rank 的完成票据对齐后统一提交恢复状态。实验通过比较两侧完整位置序列验证恢复进度一致性。普通 L2 与私有快照采用独立预算，挂起请求的快照在恢复前保持固定引用；快照容量不足时执行框架的请求中止策略。

## 3. 混合状态与恢复边界

以 T 表示已经计算完成的 Token 数，对应有效位置区间 [0,T)。恢复检查点统一记录 Attention KV、GDN 递归状态和卷积历史的上下文边界 T，保证三类状态在续算时一致。

| 状态 | 保存粒度及精度 | 恢复方式与约束 |
| --- | --- | --- |
| Attention KV | 缓存组中的 Token 历史块；BF16；按本地 KV Head 切分 | 按字段复制有效载荷，以检查点边界限定有效 Token 范围 |
| GDN recurrent state | 自然计算边界 T 的状态槽位；FP32；按本地 Head 切分 | 从已保存的自然检查点恢复 T 对应的递归状态 |
| Causal convolution history | 与 GDN 检查点配套的近期投影样本；BF16 | 与递归状态一起恢复，保留续算所需的卷积窗口 |
| 请求槽位状态 | 活跃请求槽位状态的序列化镜像 | 恢复到新的请求槽位，并校验请求身份；与缓存块恢复共同完成 |

正常恢复测试选择 T=128 和 T=129。先计算长度为 T 的前缀，再只清除 Device 索引而保留 Host，随后提交长度 T+1 的请求。实际恢复位置分别为 128、129，新请求只计算位置 128、129 上的一个新增 Token，不需要重放已经恢复的前缀。小预算下未命中的请求从位置 0 处理完整 Prompt，耗时计入请求总时延。

活跃请求测试输入长度为 130，连续输出 20 个 Token。与不中断执行比较，各次 Forward 的完整位置序列一致。首次 Prefill 覆盖位置 0 至 129，各步输出所对应的末尾位置为 129 至 148，其后通过逐步 Decode 推进，没有额外的前缀重放。因而本次正常命中和活跃快照恢复没有单独的旧上下文重放区间；预算未命中的完整 Prefill 则明确计入重算工作。

## 4. 功能正确性与资源回收

### 4.1 判据与覆盖

本实验使用两类参考。命中恢复时，与相同 TP 配置、相同检查点边界的 Device 直接复用比较，要求完整词表 Logits、采集的首个 GDN 层递归状态及卷积历史逐位一致；未命中时与完整 Prompt 的冷执行比较。生成 Token 还与冷执行参考核对。

为控制计算形状对 BF16 舍入的影响，逐位比较采用相同 TP、相同检查点边界的执行路径。冷执行分别用于未命中请求的数值对照及生成 Token 核对。

在传输层，对实际搬运的所有声明缓存字段逐字节检查，覆盖各层 KV、递归状态和卷积历史；模型状态的详细抓取覆盖首个 GDN 层，其他层通过实际搬运字节和全模型 Logits 检验。功能运行允许同步以核对字节，性能运行关闭数值抓取和字节验证。

| 测试 | 模型与 TP | 结果 |
| --- | --- | --- |
| T=128/129 卸载后续算，各输出 8 Token | 0.8B、4B；TP=1、2 | 实际 Host 加载发生，检查点、Logits、采集状态及生成结果通过 |
| 三个不同会话交替三轮，各输出 8 Token | 0.8B、4B；TP=1、2 | 9 次交替请求均恢复到 T=129，未出现跨会话状态串用 |
| Host 预算缩小至 4 个父块 | 0.8B；TP=1 | 全流程累计 149 次容量淘汰；9 次交替请求均未命中并正确重算 |
| 重复清理 Device、恢复和再次分配 | 0.8B、4B；TP=1、2 | 块地址复用，结束后活动引用和 Host pin 均为 0 |
| 主动抢占与快照恢复，输出 20 Token | 0.8B；TP=1、2 | 每个 rank 均发生 20 次 snapshot store 和 20 次 restore；20 步与不中断参考逐位一致 |

两个模型的普通大预算功能运行中，每个 rank 均记录到 11 批 H2D 加载。TP=2 的 0.8B 两侧分别恢复 123,973,632 字节，4B 两侧分别恢复 327,352,320 字节；两侧均完成本地状态恢复，且完整计算位置一致。

### 4.2 HBM 回收与块复用

以下取 T=129 后清理 Device 索引的操作。此时没有活跃请求，清理前仍保留 4 个 Device 缓存父块，清理只释放 Device 索引，不清除 Host 副本。

| 模型 | TP | 每 rank 可用父块总数 | 清理前已占用 / 空闲 | 清理后已占用 / 空闲 | Host 已缓存子块数，前 → 后 |
| --- | ---: | ---: | --- | --- | --- |
| 0.8B | 1 | 8 | 4 / 4 | 0 / 8 | 5 → 5 |
| 0.8B | 2 | 8 | 4 / 4 | 0 / 8 | 5 → 5 |
| 4B | 1 | 16 | 4 / 12 | 0 / 16 | 5 → 5 |
| 4B | 2 | 16 | 4 / 12 | 0 / 16 | 5 → 5 |

后续请求在空的 Device 索引下重新匹配 Host 并加载。0.8B TP=1 的实际记录中，同一 Device 块先用于一次恢复请求，随后重新分配给另一个会话的恢复请求，两次载荷检查均通过。该记录结合清理后的空闲块增长，提供了真实回收、重新分配及跨请求复用证据。

开启卸载的功能运行记录到 Device 缓存缓冲区大小：0.8B TP=1 为 108 MiB，TP=2 每 rank 为 54 MiB；4B 分别为 544 MiB 和 272 MiB，包含布局保留空间。上述数字仅统计缓存缓冲区，模型权重和工作区另行占用 HBM。块回收后预分配缓冲区保持分配状态，因此本实验采用空闲块变化和跨请求复用记录衡量回收效果。

完整功能序列最后清空缓存时，Device 空闲父块分别恢复到 8、16；Host 空闲父块恢复到对应预算，活动引用和 pin 为 0。主动抢占测试的私有快照池在结束后恢复为 16 个空闲父块。回归测试覆盖块边界、空搬运、填充区保护和重复使用元数据，最终为 100 项通过、7 项跳过；真实 Ascend DMA 与自动后端选择的字节往返测试均通过。

## 5. 容量与性能对照

### 5.1 工作负载与统计口径

性能对照在 TP=1 下进行，每个模型分别运行关闭卸载、Host 比例 0.5、Host 比例 4 三组，保持 Device 父块数分别为 8、16。每组先预热，再测试两种访问模式：

- 高复用：三个不同会话按固定顺序重复四轮，共 12 次请求。
- 低复用：每次更换前缀，共 12 次请求，不重复已有 Prompt。

每次输入 258 Token、生成 8 Token。每种模式输出共 96 Token，六组运行共计 144 个测量请求。时延指标采用请求总时延的中位数；吞吐按该模式 96 个输出 Token 与 12 次请求总耗时之比计算。模型加载、预热及控制命令不计入请求时延，测量模式内的冷请求、恢复和重算均计入。

命中/未命中依据响应的有效前缀 Token 数统计；是否实际来自 Host，另由真实 H2D 操作确认。实际 Prefill Token 数为各请求输入长度减去恢复前缀长度之和；重复 Prompt 重算量只统计同一访问模式中已经出现过的相同 Prompt，区别于首次冷计算。

较大 Host 预算使 0.8B 的请求时延中位数下降 21.2%，吞吐提高 43.9%；4B 分别下降 41.6%、提高 70.9%。实际 Prefill 工作量分别减少 37.2% 和 49.6%，表明收益来自已计算前缀的保存与恢复。两组命中率均为 6/12，统计范围包含冷请求。

关闭卸载的两组均通过缓存淘汰和重复请求 Prefill 完成全部测试。相同 Device 预算下，Host 缓存减少了部分重复计算，构成性能差异的主要来源。

小预算下，0.8B、4B 分别写回约 1.22 GiB、3.22 GiB，却没有一次有效 H2D 恢复，重复 Prompt 重算量也没有下降，说明预算不足会导致缓存抖动。大预算仍可能淘汰旧检查点，但能够保留足够的可复用内容，从而减少后续计算。

性能序列采样到的 Device 最小空闲父块数，0.8B 三组均为 0；4B 关闭、小预算和大预算分别为 2、2、1。该指标采用请求边界采样。各组 Device 总预算保持不变，Host 缓存通过保留已回收 Device 块的历史状态，扩大了可复用工作集的容量。

活跃抢占实验另设独立快照池，0.8B TP=1 额外分配 192 MiB，TP=2 每 rank 额外分配 96 MiB，不计入上表普通 L2 占用。请求槽位信息的序列化开销单独统计，不混入缓存 DMA 载荷。

## 6. 实验范围与结论

本次性能实验采用顺序提交的高、低复用访问序列，数值抓取、逐字节核对和主动抢占测试独立进行。测量基于共享硬件，每种访问模式包含四轮请求，结果用于评价固定 Device 预算下的复用收益与搬运代价，结论适用于本次顺序请求负载与测量条件。进一步评估可扩展到多次独立重复、并发负载，以及预取、传输计算重叠和硬件感知淘汰策略。

1. 在现有 TokenSpeed 框架上，Ascend 的 HBM—Host 两级缓存完成了实际写回、Device 块回收、重新分配和按需恢复；0.8B、4B 均通过 TP=1、TP=2 验证。
2. 统一检查点边界实现了 KV、GDN 递归状态及卷积历史的一致恢复。相同 TP、相同检查点的恢复结果与直接复用逐位一致，主动抢占后的 20 步续算也与不中断参考一致。
3. Host 预算和访问复用共同决定收益。大预算在高复用场景下分别提高约 43.9%、70.9% 的吞吐；低复用场景没有明显收益。
4. 小预算会发生频繁淘汰并消耗搬运带宽，却不一定减少重算。本实验的小预算组产生大量 D2H 写回而没有有效 H2D 恢复。
